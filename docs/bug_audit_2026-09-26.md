## 本次新增发现与修复计划

优先级：P0 是扩大实机异步测试前的门槛；P1 是核心正确性修复；P2 是恢复能力与诊断完善。优先级不等于问题已经在实机发生。

| 编号 / 优先级 | 现象与证据等级 | 定位 / 原因 | 修复与验收 |
|---|---|---|---|
| A01 / P0 | RTC 控制路径仍可能被图像处理及共享队列拖慢；代码确认，未测实机阻塞时长 | `loop.py:2767` 在总线线程调用 `latest_rgb_map()`、构建 frame；`cameras.py:210` / `544` 在锁内复制整幅 BGR，再转换 RGB；`ActionQueue` 取动作、读尾部和 merge 共用锁，锁内有张量 clone；`loop.py:2814` 还逐项转预测轨迹 | 观测组装、预处理、推理、后处理、批量转 CPU、预览全部移出控制线程；发布有界 CPU 动作时间线；慢相机/推理/预览注入不能使发送等待这些工作 |
| A02 / P1 | 关闭主画面显示导致策略丢失相机；内存复现 | `cameras.py:1026` 要求 `show_main and feed_robot`，但 `loop.py:2876` 特征声明只要求 `enabled and feed_robot`，两者不一致 | 推理选择只依赖 `enabled && feed_robot`；显示选择独立；覆盖四种 show/feed 组合、禁用、远端/本地相机和 rollout 启动校验 |
| A03 / P0 | rollout 未对观测年龄和多相机时间差设有效性门槛；代码审核风险 | 当前 `latest_rgb_map()` 返回数组，rollout 不携带帧序号/接收时间；后台可能重复用旧观测。队列不足时保持目标，但没有独立的长期缺货/陈旧观测退出规则 | 引入有时间戳的 ObservationSnapshot、最大年龄/跨相机时间差、启动 preflight；短缺进入 holding，超阈值退出或要求恢复；断流但保留最后图像、缺相机、慢推理均须测试 |
| A04 / P1 | 时间轴把新 chunk 标成已执行，但它可能尚未发布；内存复现 | `rollout_timeline.py:149` 以 qsize 降低或 index 归零激活最新 pending；模型函数返回后，后处理/延迟校验/merge 尚未结束，旧队列消费也会触发。被丢弃的结果同样可能留作 pending | 显式记录 `inference_started / cpu_ready / accepted / first_dispatched / discarded` 与 chunk ID；控制线程在成功发送后确认执行；模型计时与端到端耗时分开。丢弃结果、发布前消费旧块不得出现执行标记 |
| A05 / P1 | 清空运行覆盖后仍沿用上次值；内存复现。模型内部对象与 config 不一致为代码审核风险 | `policy.py:72` 原位改 config，空覆盖不恢复 checkpoint 基线；校验失败也无回滚。ACT `temporal_ensembler` 在构造期创建，单改 coeff 不保证对象重建，启用时还可能缺对象 | 保存不可变 checkpoint 基线；按会话构造、校验完整配置后原子应用；区分可热改、需重建 session 对象、需重新加载的字段；禁止任意结构字段原位覆盖。验证 A→B→空恢复、失败回滚、ACT 开关/系数变化、同权重缓存只载入一次 |
| A06 / P1 | RTC 时间对齐与控制时间没有统一契约；代码审核风险 | `rtc.py:498` 分别读 index、raw tail、processed tail，可能跨越消费；`new_delay` 来自耗时 / policy 周期，而 Monitor 落后时跳过 deadline、每次只 pop 一项。队列耗尽时仍按墙钟裁剪，需要明确 bootstrap/hold 语义 | 使用同一 observation origin、timeline version、冻结前缀和控制逻辑时间；控制端单独接受结果并丢弃过期段；bootstrap 从 CPU ready 后建立时间原点。不得简单把 wall time 全部换成 pop 数；停顿后动作和状态必须重新对齐 |
| A07 / P1 | 运行中 reset 会与推理/处理器状态并发；依赖层代码审核风险 | `rtc.py:369` 在 obs 锁外调用 policy/pre/post reset；epoch 只防止结果 merge，不能保护处理中间状态。Monitor 当前启动时 reset，尚未证明其常用路径触发此竞态 | reset、任务切换及 runtime config 由推理所有者串行处理；控制端先撤销 epoch，旧结果立即无效；注入阻塞推理并在此时 reset，验证无并发状态修改、无旧结果复活 |

关于 GPU 同步需准确表述：SmolVLA 默认 postprocessor 包含 `to_cpu`，不能说当前每个动作必然在控制线程等待 GPU。但 `_action_pose()` 支持的通用路径会 `.to("cpu")` / `.cpu()`，共享队列还保存 raw GPU tensor；现有接口没有保证总线线程只接触已完成的 CPU 数据。A01 的修复目标是建立这个保证。

### 三个最小复现结果

本次使用内存假对象与假时钟，没有打开设备或加载权重：

1. 相机 `enabled=True, feed_robot=True, show_main=False`：`latest_rgb_map()` 的 key 为 `[]`；仅改 `show_main=True` 后为 `["front"]`。
2. 时间轴先观察旧队列 `(qsize=10,index=0)`，记录一个新推理结束，在未发生新 chunk merge 的情况下观察旧队列 `(9,1)`：新块 `active=0.2`，误标为执行。
3. config 初值 `n_action_steps=50`，覆盖为 8，再应用空覆盖：值仍为 8。
